# 三个项目的内容、个人适配与竞争优势

这份分析依据三个项目原始 brief、个人 CV 和暑期实习总结。表中的“已有证据”指材料能支持的个人经历；“建议方案/建议职责”是未来可以承担的工作，不代表已经实现。未掌握其他组员和竞争团队的履历，因此这里只判断个人匹配程度，不预测中标概率。

## 1. UoN Pacman

### 计划到底要做什么

负责人是 Graham Hutton，预计完成时间为 2027 年 5 月。用户在迷宫里吃点和水果，避开四个性格不同的幽灵。项目明确要求 **从零实现，并尽量接近原版的 look and feel**，涉及图形、声音和复古游戏编程；时间允许才加入自创玩法。[原始 brief，第 1 页](</Users/markyang/Projects/UNUK-Year-3/CV/pdf/UoN-Pacman (Graham Hutton).pdf>)

第 2 页的 Requirements/Skills 框实际为空，没有指定 Java、JavaFX 或任何引擎。硬件框虽然勾选，但说明是团队愿意时才做街机机柜，因此机柜属于可选扩展。不能把自选技术栈、附加功能或机柜写成项目方的硬性要求。

它的难点不只是“角色能移动”。需要把移动与转向、墙体/角色碰撞、吃点计分、生命与关卡、幽灵的差异化行为、反馈与节奏组合成一致体验。菜单、暂停、重启以及清晰的运行说明也有助于完成可演示的软件。这些是从目标推导出的实现与验收建议，应在需求确认时与负责人核对。

### 你的经历如何对应

| 项目需要的能力 | 你的真实经历 | 可迁移的价值与边界 |
|---|---|---|
| 可预测的状态更新 | 修复 Go 链码历史/生命周期排序，保持确定性和账本兼容 | 能说明你会查找偶发逻辑缺陷、定义稳定输出；这不是已做过游戏状态机的证据 |
| 边界与回归测试 | 4 类根因对应 10 项失败用例，补充 ASCII/中文 999/1000 字符测试 | 可迁移到地图边缘、同时碰撞、关卡结束等规则用例；已有测试对象是链码 |
| 核心逻辑与界面解耦 | 安全 AI Demo 从 Streamlit 页面抽离分析服务 | 可用于把游戏规则与绘制/输入/声音分开，让规则能脱离 GUI 测试 |
| 可重复构建与集成 | Docker Compose/WSL 本地平台，自动启动和端到端检查 | 能帮助团队明确依赖、提供启动流程和演示前检查；已有成果是业务平台，不是游戏打包 |
| 协作交接 | 医疗后端数据库/网关审计、联调前提与发布交接文档 | 能在组员模块交接时明确接口、状态约定和运行限制 |

### 你的竞争优势应该怎么讲

最强的角度是“能把玩法逻辑做得可验证，并把团队模块稳定地接起来”。4 类根因、10 项失败用例和最终交付包复测，比泛泛的“擅长解决问题”更能说明做事方法。11 项本地 Java 单元测试与 12 个业务页面验收也能证明你会同时检查模块与完整路径。

CV 因此先展示 Go 修复、测试与本地验收，再展示 UI/服务分离，最后补充 Java 后端与学术项目。图像分类保留为软件组织和可重复部署证据，AI 技术栈不会抢走游戏工程的重点。

### 建议职责与实现顺序

建议承担游戏模型/规则、自动测试、构建与集成，不预设自己是组长。可以优先使用你已有基础的 Java；JavaFX 等 GUI 方案需要团队试验后决定，CV 没有声称你已经掌握它。

1. 先确认原版保真范围与可用素材，定义状态、输入和更新接口。
2. 打通“迷宫 → 移动/碰撞 → 吃点/计分 → 输赢/重启”的最小可玩闭环。
3. 再实现四个幽灵的行为差异，并逐项核对原版规则与操作感。
4. 为地图边界、转向、碰撞、暂停和重置建立回归用例；用固定输入/时间步长复现逻辑错误。
5. 最后改善图像、声音与操作反馈；新增玩法和机柜放在基线完成之后。

当前材料没有完整游戏、游戏引擎、JavaFX 图形或音频项目。后续若补一个小型可玩原型，最有用的证据是可运行构建、规则测试和明确的原版对照，而不是提前把待学技术写成技能。

## 2. UoN AI Game Player

### 计划到底要做什么

正式标题是 **Implementation of an AI player for a game**，负责人是 Kristian Spoerer，预计 2027 年 5 月完成。目标是实现一个有足够复杂度的知名游戏，让人类与 AI 一对一对战。语言方面，C/C++/C#/Java 等通用语言的编程能力和团队合作是高度期望的能力。[原始 brief，第 1–2 页](</Users/markyang/Projects/UNUK-Year-3/CV/pdf/UoN-AIGamePlayer (Kristian Spoerer).pdf>)

明确交付物共有五项：游戏本体、**Monte Carlo Tree Search（MCTS）对手及用户可选能力等级**、易用且美观的 GUI、软件工程设计文档、用户手册。LLM Agent、ResNet 或简单的固定规则 AI 都不能单独替代指定的 MCTS。

MCTS 可以理解为反复“选择已有分支 → 扩展新局面 → 模拟后续对局 → 把结果反馈到树中”，逐渐把计算集中在更值得探索的动作上。难度可通过搜索次数或时间预算等方式控制，但不同配置是否形成可区分、可用的能力等级，需要实验验证。

### 你的经历如何对应

| 明确要求 | 你的真实经历 | 可迁移的价值与边界 |
|---|---|---|
| AI 实现与结果评估 | ResNet18 迁移学习、数据增强、优化器对比、模块化训练/评估 | 能组织基线、参数比较和重复实验；神经网络训练不等于 MCTS 实现经验 |
| 受控的状态与执行流程 | LangGraph planner/executor/tool/replanner，线程状态与记忆，7 类工具 | 对状态、路由、终止和错误展示有实践理解；LangGraph 的规划不是蒙特卡洛树搜索 |
| 通用语言与规则实现 | Java/Spring Boot 后端、Go 链码修复，CV 列有 C/C++ | Java 和 Go 有具体工程证据；C/C++ 仅作为已有语言能力列出，不添加未提供的项目 |
| GUI 与核心分离 | Streamlit 原型、分析服务抽离、Flask 推理接口 | 具备界面/服务边界意识；没有据此声称已有桌面游戏 GUI 或异步搜索经验 |
| 设计说明与用户手册 | API/环境审计、验收步骤、使用/联调文档 | 能把规则接口、搜索配置和启动方式整理成可交接材料 |
| 团队集成与验证 | Java 单元测试、Go 回归、本地平台端到端检查 | 有助于防止 AI 出非法动作、状态拷贝污染以及只测单个算法不测完整游戏 |

### 你的竞争优势应该怎么讲

优势是“AI 背景 + 可验证的软件工程实践”。你不只是调用一个模型：学术项目有实验与评估流程，实习又有状态控制、错误处理和回归经验。这组合适合把 AI 对手做成有清晰难度、有性能边界、能通过 GUI 使用的成品。

CV 将 AI 原型与学术评估放在显著位置，同时保留 Java/Go 和文档交接。MCTS 只在 Profile 中作为目标贡献方向出现，没有放进已掌握技能或已完成项目。

### 建议职责与实现顺序

建议承担 MCTS 实现/评估、游戏规则测试及设计说明，GUI 工作与擅长前端的组员协作。具体游戏要经负责人认可；Connect Four、Reversi 可以作为讨论候选，而非已经选定的结果。

1. 确认游戏复杂度，先实现合法动作、状态复制、胜负判断和一个简单基线对手。
2. 在无 GUI 的环境里实现 MCTS，固定随机种子便于比较，并测试搜索是否修改了真实棋盘。
3. 用不同搜索预算做能力等级实验，记录每步耗时、非法动作次数和对基线的胜率。固定种子只能辅助复现，胜率仍需多局、换先后手与多种种子评估。
4. 将搜索放在独立任务/线程中，保证界面可响应，并处理退出、重开和超时；具体线程模型由选定技术栈决定。
5. GUI 显示当前玩家、可选动作、难度和结果；同步交付设计文档与用户手册。

应优先补 MCTS/UCT、树节点统计、搜索终止、状态深复制和 GUI 生命周期。不能把实习里的 LLM Planner 当成已经完成了这里的算法要求，也没有依据宣称强化学习训练经验。

## 3. CGI Crisis Reporting App

### 计划到底要做什么

项目联系人为 CGI 的 Marie Ribeiro 和 Martin Thompson，brief 的 Company 栏写 University of Nottingham，文件名为 CGI-CrisisApp。目标是做一个移动优先或 Web 原型，让某类真实用户能够报告某个地点的 concern，并让授权审核者验证、跟进和关闭。场景可以是设施、安全、活动、无障碍等，团队需要自己把用户、边界和假设讲清楚。[原始 brief，第 1–3 页](</Users/markyang/Projects/UNUK-Year-3/CV/pdf/CGI-CrisisApp.pdf>)

它明确是 **受控学生项目原型**，无需处理真实紧急事件或实时应急响应。主要闭环为：提交描述/类别/紧急程度（照片可选）→ 捕获或核验位置 → 后端入库 → 管理员审核/拒绝/改状态/记备注/升级/关闭 → 保留状态历史和审计信息。

硬性内容包括问题定义、用户报告流程、位置功能、API/服务层、报告/用户角色/位置/历史/审计的数据设计、审核流程、隐私与责任讨论、端到端演示。技术栈没有规定。热力图、通知、公开动态、重复检测、离线草稿等是可选扩展，不能只做一个漂亮仪表盘就漏掉必需闭环。

### 你的经历如何对应

| 项目要求 | 你的真实经历 | 可迁移的价值与边界 |
|---|---|---|
| API 与 UI/数据分离 | Spring Boot 4 个 GET 接口、Service/DTO/VO/异常处理；AI Demo 服务抽离 | 熟悉分层与接口契约，但已有 GET 接口不是报告创建/修改/权限接口的现成实现 |
| 数据与历史模型 | SQLite 存上传、任务、结果、来源行与失败原因，重启后可追溯 | 直接支持报告/附件/状态事件的建模思路；不能把任务历史说成已实现管理员审计或访问控制 |
| 安全关切与分类统计 | 工厂隐患分析、法规引用、风险排行、类别/区域统计 | 与上报 safety concern 的领域相近，能帮助设计分类、证据和筛选；工厂样例不能宣称校园用户验证 |
| 防止错误成功提示 | SQL 无数据/异常区分，图像回退，多文件部分失败 | 可以把“提交失败/附件失败/审核失败”设计成可理解状态，避免用户误以为已经完成 |
| 审核验证与责任边界 | 10 条合规规则正反样例，脱敏/证据不一致验收，接口与交接材料 | 能组织真实失败路径并说明系统限制；没有独立实现这些规则的底层模型或接口 |
| 完整运行与验收 | 11 项本地单元测试、Fabric 12 页面及真实本地提交验证 | 能覆盖从界面到存储的完整路径，但不能声称目标医疗环境已上线 |
| 认证、角色和个人数据 | 有最小暴露、参数化 SQL、只读审计等工程实践 | 是安全意识证据；尚无独立设计生产认证/RBAC/隐私制度的证据 |

### 你的竞争优势应该怎么讲

这是三项中最容易用真实成果解释个人价值的项目。医疗后端证明你能开发接口和处理既有系统约束；隐患助手证明你理解报告分类、来源和历史；合规验收证明你会检查失败、脱敏和材料不一致。三个证据能串成“提交 → 数据 → 审核 → 可追溯结果”的工程叙事。

CV 因此先展示 Java/API 与本地测试，再展示安全报告的数据历史与界面，随后展示合规验收与兼容性修复。区块链被压缩为验证和兼容性证据；项目不需要因为你有 Fabric 经历就加入区块链。

### 建议职责与 MVP 方案

建议承担 API/数据库、状态转换、审计记录与验收；前端、位置核验和用户研究可以与对应组员配合。建议先选“校园设施与非紧急安全关切”这类有限场景，使用合成用户、报告、照片和位置数据演示。

- **上报界面：** 描述、类别、紧急程度、已知地点、可选附件，提交后返回明确编号与状态。
- **位置：** 先支持楼宇/房间选项和已知地点 QR；位置 ID 由服务器验证。QR 可识别地点，但截图或复制 QR 不能证明提交者就在现场，应在假设中写明。
- **后端/存储：** 可使用已有基础的 Spring Boot + MySQL；至少区分 Report、Location、User/Role、Attachment、StatusEvent/AuditEvent。创建/读取/更新与审核接口统一校验输入和对象权限。
- **审核流程：** 待审核 → 已确认/已拒绝 → 处理中 → 已关闭；每次变更写操作者、时间、原因和前后状态。升级可以先表现为分派/标记，不承诺连接真实应急服务。
- **隐私与防滥用：** 仅授权角色访问相应报告，限制附件类型/大小，避免日志保存敏感正文，明确数据留存/删除策略，演示伪造位置、重复上报、越权和虚假关切的处理。
- **验收：** 至少演示合法提交、错误位置、附件失败、未授权访问、无权改状态、重复审核、关闭后历史可查，以及窄屏键盘/辅助操作可用性。

前端框架应按组员技能选，不把 React/Vue/RBAC/QR 等写成你的已实现项目。MVP 先由人工审核并保留证据；LLM 自动判断紧急程度不是必需功能，容易额外增加误判与解释负担。
